# Toolchain

> The `dotnet` CLI is the single entry point to the .NET toolchain — it drives MSBuild, NuGet, the compiler, the test runner, formatting, and analyzers.

---

## What is it?

The .NET toolchain is a set of tools that ship with the SDK, all reachable through one command: **`dotnet`**. Under it sit:

- **MSBuild** — the build engine that reads `.csproj`/`.sln` files and orchestrates compilation.
- **Roslyn** — the C# compiler and analysis platform.
- **NuGet** — package restore and management (see [Packages and NuGet](packages-and-nuget.md)).
- **`dotnet test`** — the test runner (see [Testing](testing.md)).
- **`dotnet format`** — the code formatter.
- **Roslyn analyzers** — static analysis rules that run during build.

One consistent CLI works identically on Windows, macOS, and Linux.

---

## Why does it matter?

Because everything routes through `dotnet`, local development and CI use the same commands — no separate build scripts. Formatting and analyzers are built in rather than bolted on, so code style and common bug classes are enforced at build time. Learning this small command surface covers the entire build-test-publish lifecycle.

---

## How it works

### Everyday commands

```bash
dotnet restore     # resolve and download NuGet dependencies
dotnet build       # compile (restores first if needed)
dotnet run         # build and run the project
dotnet test        # discover and run tests
dotnet publish     # produce a deployable output (see Deploy)
dotnet clean       # remove build artifacts
```

`dotnet build` produces IL assemblies under `bin/`; intermediate files go under `obj/`. Both are build output and should be git-ignored.

### Build configurations

`Debug` (default) includes debug symbols and no optimizations; `Release` optimizes and is what you ship:

```bash
dotnet build -c Release
dotnet run -c Release
```

### Formatting

`dotnet format` applies the style rules defined in an `.editorconfig` file and fixes many analyzer violations:

```bash
dotnet format               # fix formatting in place
dotnet format --verify-no-changes   # CI: fail if anything is unformatted
```

An `.editorconfig` at the repo root is the single source of truth for style — indentation, naming conventions, `var` usage, and analyzer severities.

### Analyzers

Roslyn analyzers run during compilation and surface warnings or errors for correctness, style, and performance issues. The SDK ships built-in analyzers; enable the stricter set and treat findings seriously:

```xml
<PropertyGroup>
  <AnalysisLevel>latest</AnalysisLevel>
  <EnableNETAnalyzers>true</EnableNETAnalyzers>
  <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
</PropertyGroup>
```

Add third-party analyzer packages (e.g. StyleCop.Analyzers) as normal NuGet references; they plug into the same build step.

### Global and local tools

`dotnet tool` installs CLI tools distributed as NuGet packages — globally, or pinned per repository via a tool manifest:

```bash
# global
dotnet tool install -g dotnet-ef

# local (creates/uses .config/dotnet-tools.json)
dotnet new tool-manifest
dotnet tool install dotnet-ef
dotnet tool restore        # CI restores the pinned tools
```

Local tools keep the exact tool versions in version control, so every machine and CI run uses the same ones.

---

## Examples

A typical CI verification sequence — restore, format check, build with warnings-as-errors, test:

```bash
dotnet restore --locked-mode
dotnet format --verify-no-changes
dotnet build -c Release --no-restore
dotnet test -c Release --no-build
```

`--no-restore` and `--no-build` reuse the previous step's output so each stage does not redo work.

---

## When to use

- **`dotnet` CLI** for everything: build, run, test, publish — locally and in CI.
- **`.editorconfig` + `dotnet format`** to enforce one consistent style across the team.
- **Analyzers with `TreatWarningsAsErrors`** to catch bugs and style drift at build time.
- **Local tool manifests** to pin CLI tool versions per repository.

---

## When NOT to use

- **Do not commit `bin/`, `obj/`, or `.vs/`** — they are regenerated by restore/build.
- **Do not skip `--no-restore`/`--no-build` awareness in CI** — redundant restores and rebuilds slow pipelines and can mask staleness.
- **Do not disable analyzers to silence a warning** — fix the issue or suppress the specific rule with justification in `.editorconfig`.
- **Do not rely on global tools in CI** — pin them in a manifest so builds are reproducible.
